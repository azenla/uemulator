# CPU

## State (`Env`, `#[repr(C)]`, pointed to by a pinned host register in the JIT)

- 16 GPRs (u64), `rip`, `rflags` (without lazy bits), segment regs (selector, base, limit, attrs) incl. hidden parts, GDTR/IDTR/LDTR/TR
- CR0, CR2, CR3, CR4, CR8 (stored only), EFER, STAR/LSTAR/CSTAR/SFMASK, KERNEL_GS_BASE, FS/GS base, TSC_AUX, PAT, APIC base (stub), MTRR msrs (stored)
- lazy flags: `lazy_op`, `lazy_size`, `lazy_dst`, `lazy_src`, `lazy_src2` (QEMU calls these `cc_*`)
- x87: 8×80-bit regs (stored as raw 10 bytes + software softfloat ops), FCW/FSW/FTW, MXCSR, XMM0–15 (u128)
- pending interrupt state, `halted`, `exit_request`, icount, soft TLB arrays (see 04)
- hflags cache: CPL, code size (16/32/64), addseg, SS32, protected/real, used in TB key

## Decoder (`decode.rs`, `tables.rs`)

Table-driven, one-byte, 0F, 0F38, 0F3A maps; prefix handling (66, 67, F2, F3, REX, segment overrides, LOCK); ModRM/SIB/disp/imm; RIP-relative; operand size and address size per mode. Table entry: mnemonic class, operand specs, flags-effect class, whether it can fault. Output: `Insn { len, op, operands, ... }` consumed by `translate.rs` which emits uops.

Coverage priority (what Linux + Debian userspace uses):
1. Integer: mov/movzx/movsx(d), lea, add/or/adc/sbb/and/sub/xor/cmp/test, inc/dec/neg/not, mul/imul/div/idiv, shifts/rotates/shld/shrd, bt*/bsf/bsr/popcnt/lzcnt/tzcnt (only if advertised), setcc/cmovcc/jcc, push/pop, call/ret/leave/enter, jmp, loop*, string ops with rep (movs/stos/lods/scas/cmps), xchg/cmpxchg/cmpxchg16b/xadd (lock is a no-op), cdq/cqo/cbw family, bswap, cpuid, rdtsc, rdtscp?, rdmsr/wrmsr, syscall/sysret, sysenter(no), swapgs, int/int3/iret(q), hlt, cli/sti, in/out/ins/outs, lgdt/lidt/ltr/lldt/sgdt/sidt/str, mov cr/dr, invlpg, wbinvd (nop), lfence/mfence/sfence, clflush, pause, ud2, xgetbv (not advertised; #UD).
2. SSE/SSE2 integer and scalar/packed FP used by libc memcpy/strlen/etc: movdqa/u, movq/d, movaps/ups, pxor/por/pand/pandn, padd/psub, pcmpeq/gt, pmovmskb, pshufd, punpck*, packss/usb, psrl/psll/psra, shufps, paddq, pmuludq, cvt*, add/sub/mul/div/sqrt/min/max ss/sd/ps/pd, comisd/ucomisd, movmsk. SSE3, SSSE3 (XMM forms only), SSE4.1, SSE4.2, PCLMULQDQ and AES-NI are implemented in `cpu/sse_ext.rs` (see "Instruction extensions" below).
3. x87: fninit, fld/fst/fstp (m32/m64/m80, st(i)), fild/fistp, fadd/fsub/fmul/fdiv family, fxch, fchs/fabs, fcom/fucom(i)(p), fnstcw/fldcw/fnstsw, fxsave/fxrstor, fwait; transcendentals later via host libm with documented precision loss.
4. Unimplemented opcode → #UD, with a one-shot log through the log hook (opcode bytes + rip).

0F 18–1F: NOP hint space (prefetch, ENDBR64 `F3 0F 1E FA`, multi-byte nops).

## Lazy flags

CC_OP-style: ALU ops store `(op, dst, src[, src2])`; flags are materialized when consumed (jcc/setcc/cmov/pushf/adc/sbb/rcl/...) or when the op class changes. Reuse the QEMU scheme conceptually (`cc_helper*`): ops per width (B/W/L/Q) for ADD, ADC, SUB, SBB, LOGIC, INC, DEC, SHL, SHR, SAR, MUL, ADCX/OX (later), plus EFLAGS (materialized) and CLR. Fork note: INC/DEC keep carry via `lazy_src`, a cheap win.

Interpreter and JIT both call the same `flags::compute_all(cc_op, dst, src, src2)`; the JIT inlines the hot cases (ZF/SF/CF from SUB/CMP/TEST/AND followed by jcc).

## Exactness rules

- An instruction commits GPR/flag writes only after all its faulting loads/stores; pushes and pops compute RSP in a temp and write it last; string ops commit per iteration (rep is interruptible, RIP stays on the instruction until RCX hits 0).
- Every faulting uop sequence is preceded by an `insn_start(rip)` that stores guest RIP to `Env` (JIT: one `str`; coalesced when there are no faulting ops in between). No unwind tables in v1.
- Exception delivery (`exception.rs`): long mode IDT gate lookup, IST, TSS rsp0, error code push, privilege change stack switch, #DF escalation, triple fault → exit. Also real-address and protected-mode 32-bit delivery only as far as the decompressor needs.
- `iretq`, `sysretq`, far calls/jumps through call gates (not needed) — implement iret and far jmp/ret with descriptor loads in long mode.
- Segment loads in 64-bit mode: validate and cache base/limit/attrs for CS/SS/DS/ES; FS/GS use MSR bases (or `rdfsbase`/`wrfsbase` and the GS pair, which need CR4.FSGSBASE).
- Page faults: CR2 + error code (P/W/U/RSVD/I), fixups via kernel `ex_table` work because RIP is exact.
- `rdmsr`/`wrmsr` on unknown MSR → #GP (kernel uses `rdmsr_safe`).

## CPUID/MSR contract

`cpu/cpuid.rs` (leaf contents tested in `cpuid_tests.rs`). The identity is an AMD Zen 4 (family 19h, EPYC 9004 "Genoa"): signature `0x00A10F11` (family 0x19, model 0x11, stepping 1), brand "AMD EPYC-Genoa Processor" (QEMU's name for the model; SKU strings carry core counts), `AuthenticAMD`. Linux names it Zen 4 ("cpu family 25 model 17") and picks the matching erratum and mitigation paths; Xen builds its policy from the raw leaves. The set is the AMD Genoa leaves (cross-checked against QEMU's `EPYC-Genoa` model, `query-cpu-model-expansion`) **minus** everything without an implementation and tests. Advertised:

- Leaf 0: max leaf 0x10. Leaf 1: EDX the classic set (no VME) plus HTT when more than one logical processor; ECX SSE3, PCLMULQDQ, MONITOR, SSSE3, FMA, CX16, PCID, SSE4.1/4.2, x2APIC, MOVBE, POPCNT, TSC-deadline, AES, XSAVE, OSXSAVE (mirrors CR4), AVX, F16C, RDRAND; EBX carries the initial APIC id (low 8 bits of the x2APIC id) and the logical processor count. Leaf 5 monitor, leaf 6 ARAT.
- Leaf 7 subleaf 0: FSGSBASE, BMI1, AVX2, SMEP, BMI2, ERMS, INVPCID, AVX512F/DQ/IFMA/CD/BW/VL, RDSEED, ADX, SMAP, CLFLUSHOPT, CLWB, SHA (EBX); AVX512_VBMI/VBMI2/VNNI/BITALG/VPOPCNTDQ, UMIP, GFNI, VAES, VPCLMULQDQ, RDPID (ECX); FSRM and the speculation-control bits (EDX, see below); EAX = 1. Subleaf 1 EAX: AVX512_BF16. Not advertised: LA57, PKU/OSPKE, CET, AVX512_FP16/VP2INTERSECT, AVX-VNNI, AVX512PF/ER, TSC_ADJUST.
- Leaf 0xB: x2APIC topology (SMT and core levels), 0xD: XSAVE with the compacted format (see "XSAVE and RDRAND"). Leaf 0x1F (Intel) is absent, as on Zen 4.
- Leaf 0x80000001: ECX LAHF_LM, CMP_LEGACY (when more than one processor), SVM, ABM, 3DNOWPREFETCH, TOPOEXT; EDX SYSCALL, NX, PDPE1GB, RDTSCP, LM and the leaf 1 aliases. Absent (not implemented): SSE4A, MMXEXT, FFXSR, MWAITX, PERFCTR_CORE, OSVW, IBS, LWP, EXTAPIC, CR8LEGACY.
- Leaf 0x80000005/6: L1 32 KiB 8-way data and instruction, L2 1 MiB 8-way, L3 32 MiB 16-way (one die), TLBs; leaf 0x8000001D enumerates the same caches with their sharing (L1/L2 per core, L3 by up to 16 threads) from the same constants, so the leaves cannot disagree (a test checks it). Leaf 0x8000001E: extended APIC id, threads per core, core id, one node.
- Leaf 0x80000007: invariant TSC. 0x80000008: 40 physical / 48 virtual address bits (not Genoa's 52/57), EBX CLZERO, XSAVEERPTR (the kernel then skips its FXSAVE-leak workaround), WBNOINVD, IBPB, IBRS, STIBP, SSBD, IBPB_RET; ECX processor count - 1 and APIC id width. 0x8000000A: SVM, see "SVM (AMD-V)". 0x80000021: EAX LFENCE_ALWAYS_SERIALIZING and SRSO_NO, ECX TSA_SQ_NO and TSA_L1_NO.
- The topology is `CpuTopology { logical_processors, threads_per_core, x2apic_id }` in `Cpu::topology` (default one processor). SMP does not exist yet; the embedder-facing knob comes with it, and the local APIC id must be set to the same x2APIC id.

Deliberate departures from the hardware, all so a guest does not run code the emulator would only slow down or cannot honour: TSC-deadline is advertised (AMD has none; the APIC model implements it and calibration is much faster); leaf 7 EDX and `IA32_ARCH_CAPABILITIES` keep the Intel spelling of the speculation-control interface (see below), and the SRSO_NO/TSA_*_NO bits claim what is true of an in-order CPU that never speculates; 40/48 address bits; no PMU, IBS, SEV or hypervisor leaves. MSRs that are stored but otherwise inert (Linux and Xen read-modify-write them with the `_safe` accessors): PATCH_LEVEL (0x8b, a real Genoa revision so Linux does not invent one), HWCR, NB_CFG, LS_CFG, IC_CFG, DC_CFG, BU_CFG2, DE_CFG, ZEN4_BP_CFG, SYSCFG, TOP_MEM/TOP_MEM2, the IORRs and the four legacy perf event selector/counter pairs (0xC0010000-7: they store but never count, and `rdpmc` reads PERFCTR0-3; Linux then enables its AMD PMU and NMI watchdog instead of printing "Broken PMU hardware detected". The counters and `rdpmc` must come together: with the MSRs but a #UD `rdpmc`, Linux oopsed in `perf_reboot` at shutdown). IA32_XSS (0xDA0) reads 0 and accepts only 0. Unknown MSRs #GP and are logged once.

Advertising a bit is a promise; add bits only together with the test that proves the instructions.

## SMP (`cpu/smp.rs`, `MachineConfig::cpus`, 1 to 64)

One host thread runs every vCPU in turns, so it works on the freestanding hosts (UEFI, wasm) and keeps the clock deterministic. There is one `Cpu` per vCPU and one `Smp` scheduler over them.

- **What is per vCPU and what is machine-wide.** Everything architectural (registers, segments, control registers, MSRs, FPU/SSE/AVX state, soft TLB, SVM state, pending exception, lazy flags, xcr0, MONITOR arm, `halted`) stays in the vCPU's own `Cpu`. The machine-wide fields (RAM, `page_has_code`, decode cache, `Devices`, the JIT and its block cache, the clock, the log/poll hooks) live in whichever `Cpu` ran last and `Cpu::swap_shared` moves them to the next one at a switch: a dozen pointer-sized swaps. The JIT finds everything relative to a `Cpu` pointer and its blocks are keyed by (rip, physical address), so it needs no per-vCPU copies; a vCPU that has not run yet owns only placeholders (`Cpu::new_secondary`). Adding a machine-wide field to `Cpu` means adding it to `swap_shared`.
- **Scheduling.** A vCPU runs until its quantum ends (the device event tick, `EVENT_INTERVAL` = 4096 instructions, so a switch happens at a block boundary), until it halts, or until it executes `pause` (a spin loop is waiting for another vCPU; `request_yield` pulls `next_event` to 0 and sets `block_exit_requested`, so the hot loop gains no test). `Cpu::run_slice` returns `Slice::{Yield, Halted, Exit}`; with one vCPU `Cpu::run` is the same loop and never yields. `Smp::run` picks the next runnable vCPU round robin. Runnable means not halted, or halted with a wake condition (`Devices::wake_pending`: an INIT/SIPI, an NMI, a deliverable interrupt with IF=1 and GIF=1, or a store to the line an `mwait` armed). The whole machine idles (`Cpu::idle`: warp virtual time to the next device deadline, or sleep in realtime mode) only when no vCPU is runnable, and ends with `Shutdown` only when every vCPU is halted with interrupts off and no NMI pending (a halted BSP with an AP still working does not end the run). A triple fault, reset or power-off of any vCPU ends the machine as with one.
- **Clock.** `icount` travels with the machine-wide state, so guest time is monotonic across switches. To make N busy vCPUs finish a parallel workload in about 1/N of the guest time, time advances by retired instructions divided by the number of vCPUs that were running when the slice began (`Cpu::start_slice`; each vCPU still sees 1 instruction per ns on average). With one vCPU the divisor is 1: `now_ns` is the old `icount + idle_skipped_ns`.
- **INIT and SIPI.** Every vCPU but 0 starts halted in wait-for-SIPI (`Cpu::new_secondary`). An INIT or start-up IPI is recorded in the target's LAPIC and acted on when the scheduler next enters that vCPU (`apply_start_signals`): INIT resets the registers to the real-mode power-on state without flushing the decode cache (`reset_real_mode_registers`) and waits; a SIPI to a waiting vCPU starts real mode at CS=vector<<8, IP=0; one to a running vCPU is ignored.
- **Coherence.** A store by one vCPU to a page holding translated code runs `code_written` on the shared JIT and decode cache, so it invalidates for all. A vCPU's private TLB may hold a write tag for a page another vCPU has since made code; `mark_code` bumps `code_mark_epoch` and `revoke_stale_write_tags` drops such tags when a vCPU is switched in. INVLPG and CR3 writes touch only the executing vCPU's TLB (the guest shoots down with IPIs). `lock`/xchg stay atomic and memory is sequentially consistent because one vCPU runs at a time.
- **CPUID** (`Cpu::smp_cpuid`, a post-processing step so the model tables stay untouched): leaf 1 EBX gets the APIC id and logical processor count and EDX the HTT bit; leaf 0xB reports the x2APIC id in EDX and the processor count at the core level; leaf 0x80000008 ECX gets the core count minus one.
- **Not supported with more than one vCPU**: `verify_jit` (lockstep), firmware images and the `boot_disk` BIOS shim (both refused by `EmulatedMachine::new`), and `acpi(false)` (the MADT is how the guest finds the others). The default stays 1: more vCPUs cost host time (they share one thread) and only exercise the guest's SMP paths.

## Instruction extensions

Dispatch: `Cpu::sse` hands everything outside the `0F` map (0F 38, 0F 3A) and every `0F` opcode it does not know to `sse::ext` (`sse_ext.rs`, a child module that reuses the SSE2 soft-float engine and lane helpers). `Op` is the decoded operation, `Source` how the second operand is read (aligned/unaligned m128, a low part, none), and the same prologue applies the SSE enable rules (#UD for CR0.EM or CR4.OSFXSR clear, then #NM for CR0.TS), the 16-byte alignment #GP and the mandatory-prefix check; an invalid ModRM form is #UD even under CR0.TS. Pure helpers: `string_compare.rs` (pcmp[ei]str[im]: SDM invalid-element table, all aggregations and polarities) and `crypto.rs` (CRC-32C table, AES S-box generated from its GF(2^8) definition, rounds, carry-less multiply).

- Integer, in `exec.rs`: POPCNT (F3 0F B8), LZCNT (F3 0F BD; plain BSR without the prefix, so the ABM bit and the arm go together), CMPXCHG16B (REX.W 0F C7 /1, #GP(0) unless 16-byte aligned, always writes), and in `sse_ext.rs` CRC32 (F2 0F 38 F0/F1) and MOVBE (0F 38 F0/F1). TZCNT (F3 0F BC) is BSF without the prefix, so it and the BMI1 bit go together (see "VEX and BMI").
- SSE3: movddup, movsldup, movshdup, lddqu, addsub/hadd/hsub (ps, pd), x87 fisttp (m16/m32/m64).
- SSSE3: all the XMM forms. The MMX-register forms (no 66 prefix) are deliberately #UD (logged once as unimplemented): glibc and the kernel only use the XMM forms, and each MMX form needs its own lane layout. The CPUID bit describes the XMM forms.
- SSE4.1: blends (immediate and xmm0-implicit), ptest, pmovsx/zx, pmuldq/pmulld, pmin/pmax, pextr/pinsr/extractps/insertps, round{ps,pd,ss,sd} (immediate mode, MXCSR.RC, precision suppression, SNaN quieting, DAZ), dpps/dppd (sum order `(p0+p1)+(p2+p3)`), mpsadbw, phminposuw, packusdw, pcmpeqq, movntdqa.
- SSE4.2: pcmpgtq, CRC32, pcmpestri/pcmpestrm/pcmpistri/pcmpistrm (all imm8 modes, REX.W lengths).
- PCLMULQDQ and AES-NI (aesenc/last, aesdec/last, aesimc, aeskeygenassist), tested with FIPS-197 appendix B and C.1 end to end.
- FSGSBASE: F3 0F AE /0../3 register forms, gated by CR4.FSGSBASE (bit 16, accepted by mov cr4), canonical check on writes.
- SHA-NI (`crypto.rs`, decoded ahead of `decode_integer_op` because these are unprefixed `0F 38 C8-CD` and `0F 3A CC`): sha1rnds4/nexte/msg1/msg2 and sha256rnds2/msg1/msg2. Tested end to end by hashing "abc" with SHA-1 and SHA-256 through the instruction flow of Intel's white paper against the FIPS 180-4 digests (this pins every function, operand order and dword layout), plus register versus memory operands, alignment and the 66-prefixed opcodes being #UD.
- ADX: `adcx` (66 0F 38 F6) and `adox` (F3 0F 38 F6), 32 and 64 bit: add with carry through CF respectively OF only, the other flag untouched (the whole 2^64 operand grid against a `u128` reference, with every flag combination).
- `clwb` (66 0F AE /6) and `clflushopt` (66 0F AE /7) are the access check `clflush` performs. `rdpid` (F3 0F C7 /7) returns IA32_TSC_AUX (64 bits in 64-bit mode). `clzero` (0F 01 FC) zeroes the aligned 64-byte line addressed by rAX (any CPL, DS-relative, truncated by the 0x67 prefix). `wbnoinvd` (F3 0F 09) is wbinvd. 1 GiB pages are `pdpe1gb`.

The JIT runs all of the above through `helper_exec` (none is a block ender, except that group 7 syncs the clock for rdtscp); `testkit::assert_jit_matches_interpreter` cases cover representative forms. Several encodings are prefix-dependent (F3 0F B8 POPCNT vs JMPE, F3 0F BD LZCNT vs BSR, F3 0F BC still BSF, 0F 38 F0/F1 MOVBE vs CRC32 by F2, F3 0F AE FSGSBASE vs the fences): any inline JIT lowering of the neighbouring opcodes must check `insn.rep` and `insn.p66`, or it silently diverges from the interpreter.


## Speculation control (mitigations)

The CPU is in-order and never speculates, so it says so, to keep the guest kernel from running mitigation code the emulator would have to interpret:

- Leaf 7 EDX: SPEC_CTRL, STIBP, L1D_FLUSH, ARCH_CAPABILITIES, SSBD; leaf 0x80000008 EBX: IBPB, IBRS, STIBP, SSBD. MSRs: `IA32_SPEC_CTRL` (0x48, bits 0-2 stored, others #GP), `IA32_PRED_CMD` (0x49) and `IA32_FLUSH_CMD` (0x10b) write-only with bit 0 only, `IA32_ARCH_CAPABILITIES` (0x10a, read-only) with every `*_NO` bit Linux 6.18 checks plus IBRS_ALL (so Spectre v2 resolves to one-time "Enhanced IBRS", no retpolines) and BHI_NO (no BHB clearing loop on syscall entry). RSBA stays clear.
- The family used to be 0x14, to dodge `VULNBL_AMD`, which matches families 0x15-0x17 for RETBLEED (a return thunk on every `ret`) and 0x19/0x1a for SRSO by number. With family 0x19 that route is closed, so the same effect comes from the CPUID bits Linux honours before it sets the bug: SRSO_NO (leaf 0x80000021 EAX) and TSA_SQ_NO/TSA_L1_NO (ECX) (family 0x19 is not on the RETBLEED list). Check the `bugs` line of /proc/cpuinfo.
- Check (Alpine 6.18 guest, `rdinit=/bin/sh`, cmdline without `mitigations=off`): every file in `/sys/devices/system/cpu/vulnerabilities` reads "Not affected" except `spectre_v2` ("Enhanced / Automatic IBRS", a single MSR write at boot) and `spectre_v1` (usercopy barriers). Before this change retbleed selected "untrained return thunk" and spectre_v2 was "Vulnerable" only because the quick cmdline passes `mitigations=off`.

## XSAVE and RDRAND

`cpu/xsave.rs`. State components: x87 (XCR0 bit 0), SSE (1), AVX (2) and the three AVX-512 ones (5-7). The standard-format area is the 512-byte fxsave image, the 64-byte header and the components at their fixed offsets (2688 bytes with everything on); the compacted format packs only the components named in XCOMP_BV behind the header (2432 bytes), with no 64-byte alignment padding because CPUID.0xD.n:ECX bit 1 is clear for all of them.

- `xsetbv`/`xgetbv` (0F 01 D1/D0): `Cpu::xcr0`, #UD without CR4.OSXSAVE (bit 18, accepted by `mov cr4`, mirrored into CPUID.1:ECX bit 27 when read), `xsetbv` CPL 0 only and #GP for ECX != 0, x87 clear, or components beyond `XCR0_SUPPORTED`. Extending that mask means extending leaf 0xD and the area layout too. `xgetbv` with ECX=1 returns XCR0 & XINUSE (`Cpu::xinuse`: the components not at their reset values, computed from the state), advertised as XGETBV1.
- `xsave`/`xsaveopt` (0F AE /4, /6) and `xrstor` (/5): #UD, then #NM (CR0.TS), then #GP(0) for a non-64-byte-aligned area. The request bitmap is EDX:EAX masked by XCR0. Saved components are always marked in use in XSTATE_BV, so `xsaveopt` is `xsave` (software can only see the difference through XSTATE_BV). `xrstor` validates XSTATE_BV, XCOMP_BV and the reserved header bytes, then reads everything before committing; a component in the bitmap with its XSTATE_BV bit clear is reset to its initial state, MXCSR is read whenever SSE is in the bitmap. fxsave/fxrstor share `save_legacy_region`/`restore_legacy_region` in `fpu.rs`. **`66 0F AE /6` is `clwb`, not xsaveopt**: it used to run as xsaveopt and would have written an XSAVE area over the operand.
- `xsavec` (0F C7 /4), `xsaves` (/5, CPL 0) and `xrstors` (/3, CPL 0, compacted format only) (REX.W forms identical): `xsave_compacted` writes the compacted layout (`Layout::Compacted { components }` computes each offset), XSTATE_BV = the requested components, XCOMP_BV = bit 63 | requested, the other header bytes zero. `xrstor` accepts a compacted area too (XCOMP_BV bit 63 set): XCOMP_BV[62:0] must lie inside XCR0 (|IA32_XSS, which is 0), XSTATE_BV inside XCOMP_BV. Linux now reports "context size is 2432 bytes, using 'compacted' format" and saves with xsaves. (The standard format was not broken: AVX-512 state survives signals and context switches in a real guest, see "Real-guest check" below; Zen 4 simply has the instructions and Xen's policy expects them.)
- `rdrand`/`rdseed` (0F C7 /6, /7, register forms): always CF=1, other arithmetic flags clear. The generator is splitmix64 in `Cpu::rng_state`, seeded by `MachineConfig::random_seed` (the CLI passes host entropy; the library default is a fixed constant, which is right for tests and `--verify` because the twin interpreter copies the state, but wrong for a guest that generates keys). Not cryptographic; the kernel mixes it with other sources. Side effect: the guest's crng is initialised at boot (`random: crng init done` at 0.05 s) instead of waiting for interrupt entropy.

## VEX and BMI

`decode` understands `c4`/`c5` (always VEX in 64-bit mode; `62` EVEX is still invalid). The result is an ordinary `Insn` with `vex`, `vex_l` and `vex_v` (un-inverted vvvv) set, R/X/B/W folded into `rex` (with `rex_present` false), `pp` in `p66`/`rep`, `opsize` from VEX.W only, and `op = VEX_OP_FLAG (0x1000) | (map << 8) | opcode`. The flag keeps VEX opcodes from matching any legacy `op` arm in the interpreter or the JIT (vex `0F38 F6` is mulx, legacy `66 0F 38 F6` is adcx; vex `0F 10` is vmovups, legacy is movups); `exec` hands `vex` instructions to `exec_vex` before the legacy dispatch, and the JIT, which only matches exact legacy ops, runs them through its interpreter helper. A legacy 66/F2/F3/F0/REX prefix in front of VEX, or a map outside 1-3, is #UD.

`cpu/bmi.rs` (CPUID.7.0:EBX bits 3 and 8): andn, bextr, blsi, blsmsk, blsr, bzhi, mulx, pdep, pext, rorx, sarx, shlx, shrx plus tzcnt in `exec.rs`. They are LZ (VEX.L set is #UD); rorx also needs vvvv = 1111. Flag behavior: andn/blsr/blsmsk/blsi/bzhi set ZF, SF, PF from the result and clear OF; CF is "source is zero" (blsr, blsmsk), "source is non-zero" (blsi) and "index > width-1" (bzhi); bextr clears CF/OF and sets ZF only; mulx, pdep, pext, rorx and the shifts leave all flags alone. Shift counts are masked to width-1, and mulx writes the low half first so the high half wins when both destinations are the same register. AF/PF are architecturally undefined for the ones that set flags; ours are 0/computed as noted. Tests (`bmi.rs`) compare against independent reference models over a spread of edge values, and `jit/diff_alu.rs::bmi_instructions` pins JIT = interpreter.

The vector VEX forms are in "AVX, AVX2, FMA, F16C" below.

## RDTSCP

`0F 01 F9`, advertised in 0x80000001 EDX bit 27: EDX:EAX = TSC (same CR4.TSD rule as rdtsc), ECX = IA32_TSC_AUX. Linux uses it for `rdpid`-less CPU/node lookup in the vDSO.

## UMIP, SMEP/SMAP, PCID/INVPCID, MONITOR/MWAIT

`cpu/protection.rs` plus the page walk in `mem.rs`.

- UMIP (CR4 bit 11, CPUID.7.0:ECX bit 2): sgdt, sidt, sldt, str, smsw are #GP(0) at CPL > 0.
- SMEP/SMAP (CR4 bits 20/21, CPUID.7.0:EBX bits 7/20): in `walk`, a supervisor-mode access (`!user`) to a page that is user-accessible at every level is #PF (P=1; the fetch bit is reported when NX *or* SMEP is on) for fetches under SMEP and for data accesses under SMAP while EFLAGS.AC is clear. `stac`/`clac` (0F 01 CB/CA) set/clear AC and are #UD outside CPL 0. **Such a translation is never put in the soft TLB** while SMEP or SMAP is on: AC changes (stac, clac, popf) without flushing, so a cached entry would let a later access skip the check. The kernel's user-copy paths are the only accesses affected, and they were slow-path walks anyway. Implicit supervisor accesses (descriptor tables) cannot be told from explicit ones inside `walk`, so they get the AC waiver too; no kernel relies on the difference.
- PCID/INVPCID (CR4.PCIDE bit 17, CPUID.1:ECX bit 17, CPUID.7.0:EBX bit 10): CR3[11:0] holds the PCID and bit 63 is accepted and ignored. The TLB is untagged, so every CR3 write and every INVPCID type flushes everything (always a legal superset); operand validation follows the SDM. PCIDE can only be set while CR3[11:0] is zero.
- MONITOR/MWAIT (CPUID.1:ECX bit 3, leaf 5 = 64-byte lines, extensions + interrupt-break): CPL 0, ECX/EDX checked. `mwait` after a `monitor` behaves like `hlt` with interrupts enabled and returns immediately with IF=0, which hardware may also do. With one vCPU only interrupts wake it (nothing but DMA can write guest memory meanwhile); with several, the monitored physical line is snapshotted and the scheduler wakes the vCPU when its contents change (`Cpu::mwait_watch`).
- Linux 6.18 guest: "x86/cpu: User Mode Instruction Prevention (UMIP) activated"; `smep smap umip pcid invpcid monitor` appear in /proc/cpuinfo; lockstep boot is divergence-free.
- Found by the lockstep verifier: `rdtscp` (group 7) reads guest time, so `jit::helpers::reads_guest_clock` now includes the whole group, otherwise the JIT read a stale `icount` mid-block.

## AVX, AVX2, FMA, F16C

Files: `avx.rs` (the wrapper and its table), `avx_special.rs` (everything else), `sse_fma.rs` (FMA, F16C and the 32 compare predicates, a child of `sse` because it needs the soft-float internals), tests in `avx_tests.rs`, `avx_special_tests.rs`, `avx_cases.rs` / `avx_special_encodings.rs` (encodings generated from the assembler; regenerate with the scripts' recipe: assemble each mnemonic with `hack/asm.sh`).

State: `Cpu::ymm_hi: [u128; 16]` holds bits 255:128; legacy SSE leaves it alone, VEX.128 zeroes it. XCR0 bit 2 enables it (`XCR0_SUPPORTED` is now 7, AVX needs SSE); XSAVE component 2 is 256 bytes at offset 576 (area 832 bytes, CPUID.0xD.2 = {256, 576, 0, 0}), saved by xsave/xsaveopt and loaded or reset by xrstor. `fxsave` does not touch it, as on hardware. `Cpu::diff` compares it, so `--verify` covers it.

Gate (`vex_gate`): #UD unless CR4.OSXSAVE and XCR0[2:1] = 11, then #NM under CR0.TS. CR4.OSFXSR does not matter for VEX.

Wrapper (`exec_vex_vector`): most VEX instructions are an SSE instruction plus a non-destructive first source, so they run through the existing SSE kernels. `vex_form` classifies each (map, opcode, pp) as: `Merge` (is the destination seeded from vvvv: always, never, or only for the register form as in vmovss), `Dest` (reg, rm, or no vector destination) and `Width` (`Pair`: 128 bits, or two lane passes with VEX.L; `Scalar`: VEX.L ignored; `Xmm`: VEX.L is #UD). A pass seeds `xmm[dest]` from `xmm[vvvv]`, calls `sse()` with `vex_active` set (which drops the OSFXSR gate and the 16-byte alignment rule, except for the explicit vmovaps/vmovapd/vmovdqa/vmovntdqa loads), and for the upper lane swaps `xmm` with `ymm_hi` and adds 16 to the displacement. Both lanes run on a snapshot, so a fault in the second leaves nothing written. **Collisions**: seeding overwrites the destination, so if the kernel still has to read it as its other operand (`vpcmpeqb ymm1, ymm0, ymm1`, the destination is also the r/m source), that operand is redirected to a scratch register first. This was found by booting Debian: glibc's AVX2 string functions use that form constantly, and a wrong remap broke `strcmp` ("applet not found" in busybox). The plumbing tests now cover it. Explicitly aligned 256-bit moves need 32-byte alignment (checked once before the passes).

`avx_special.rs`: movmskps/pd, pmovmskb (256-bit), cvtps2pd/cvtdq2pd (widening) and cvtpd2ps/cvt(t)pd2dq (narrowing, each half through the legacy kernel), shifts by xmm count (count is the low quadword of an xmm/m128, shared by both lanes) and by immediate (destination is vvvv), vptest/vtestps/vtestpd, vpermilps/pd (variable and immediate), vpermq/vpermpd/vpermps/vpermd, vperm2f128/i128, vinsert/vextract f128/i128, all the broadcasts, pmovsx/zx (the 256-bit forms widen twice as many elements, memory operands read exactly the bytes they use), vblendv* (mask register in imm8[7:4]), vpblendd, vpsllv/vpsrlv/vpsravd, vmaskmovps/pd and vpmaskmovd/q (masked-out elements are never read, written or faulted on), vldmxcsr/vstmxcsr, vzeroupper/vzeroall, vpcmpistrm/vpcmpestrm (also zero the upper half of xmm0), and the gathers.

Gathers (VSIB): the decoder keeps SIB index 4 for the 0F38 90-93 opcodes (it is xmm4, not "no index"). The mask is normalised to all-ones/all-zeros per element, each completed element clears its mask element, and a fault writes the partial registers back before reporting (restartable, as on hardware); on completion the mask register is zero and everything above the gathered elements is zeroed. #UD when destination, mask and index registers are not all different.

`sse_fma.rs`: FMA3 (132/213/231 of madd/msub/nmadd/nmsub, packed and scalar, and maddsub/msubadd) rounds once: the exact product of the two significands (at most 106 bits) is one term of `add_terms`, the same routine the legacy adder uses, so DAZ/FTZ/rounding mode/flags behave like the other soft-float instructions. NaN selection takes the first NaN in operand order (destination, vvvv, r/m), quieted; infinity times zero is invalid. Tested bit-for-bit against the host's `mul_add` for every form, with subnormals and forced cancellations. F16C: `vcvtph2ps` is exact (all 65536 inputs checked), `vcvtps2ph` rounds under imm8[1:0] or MXCSR.RC (imm8[2]) with overflow/underflow/precision flags (checked against an independent table-search reference in all four modes). The compare predicates beyond the legacy eight (imm8 8..31: the 32 SDM names, with the `_S` forms signalling on quiet NaNs) are all tested.

Not implemented: AVX-VNNI (the VEX encoding), AVX-IFMA. The JIT runs every VEX instruction through its interpreter helper. The 256-bit AES rounds, PCLMULQDQ and the GFNI instructions exist in the VEX and legacy encodings too (they are one kernel per 128-bit lane); aesimc/aeskeygenassist stay 128-bit only. Two staging bugs were found while adding AVX-512 and are fixed: `vcvtsi2ss/sd` and `vpinsrb/w/d/q` with a general register whose number equals the destination xmm number treated the register as a colliding vector operand (`rm_is_general_register`), and `vaesimc` with VEX.L=1 did not raise #UD.

## ERMS and FSRM

Advertised (CPUID.7.0:EBX bit 9, EDX bit 4). With them Linux uses `rep movsb`/`rep stosb` for memcpy, clear_page and every `copy_to/from_user`. That is only fast because `rep_bulk` handles a page of such an instruction as one host copy or fill, and because the run-loop slice is `REP_BYTES_PER_SLICE` (32 KiB) of data rather than a count of elements: counting elements gave a `rep movsb` an eighth of the bytes per round trip of the `rep movsq` it replaces, which is why the first attempt measured slower. Measured now on Alpine (interpreter + JIT): boot to shell 1.2 s either way; `dd if=/dev/zero of=/dev/null bs=64k count=30000` (2 GB through copy_to_user) 3.6 s without, 0.3 s with. Tests: `rep_slice_tests` in `exec.rs` (copies across slice and page boundaries, resume with RIP on the instruction).

## SVM (AMD-V)

`cpu/svm.rs`. Advertised: CPUID 0x80000001 ECX bit 2 and leaf 0x8000000A (revision 1, 64 ASIDs, features: nested paging, next-RIP save, VMCB clean bits, flush-by-ASID). MSRs `VM_CR` (0xC0010114, SVMDIS blocks setting EFER.SVME) and `VM_HSAVE_PA` (0xC0010117); `EFER.SVME` (bit 12). Layout and exit codes mirror `uemulator-uefi/src/hv/svm.rs`, which drives real hardware SVM.

Model: there is one CPU state, so entering a guest is a state swap. `vmrun` (0F 01 D8) validates the VMCB (APM 15.5.1: SVME in the guest EFER, CD/NW, high CR0/DR bits, CR3/CR4 reserved bits, VMRUN intercept set, non-zero ASID) and on failure completes with `VMEXIT_INVALID` in the VMCB and the host untouched. Otherwise it saves the host (RIP/RSP/RAX/RFLAGS, CR0/3/4, EFER, ES/CS/SS/DS, GDTR/IDTR, DR6/7) in `Guest::host`, loads the guest from the VMCB, flushes the TLB, sets GIF and injects EVENTINJ through the normal IDT delivery. All other GPRs are shared with the host (the hypervisor swaps them, as with hardware); FS/GS/TR/LDTR/KernelGSbase/STAR/LSTAR/CSTAR/SFMASK/SYSENTER are only moved by `vmload`/`vmsave`. #VMEXIT (`vmexit`) writes the guest state, exit code, info1/info2 and nRIP back, restores the host, clears GIF and returns `Exception::Vmexit`, which every layer treats as "the instruction is fully accounted for". `stgi`/`clgi` toggle GIF (interrupt delivery is gated on it); `invlpga` flushes the (untagged) TLB.

Intercepts, all read from the VMCB at `vmrun` and checked in the normal paths: instruction intercepts in `exec` (`svm_intercept`: cpuid, hlt, rdtsc(p), rdpmc, pushf/popf/iret, int n, invd/wbinvd, pause, monitor/mwait, xsetbv, invlpg/invlpga, the SVM instructions, sgdt/sidt/sldt/str and lgdt/lidt/lldt/ltr, CR and DR moves per register, the CR0 selective-write intercept, IOIO through the I/O permission map with the architectural EXITINFO1 encoding, RDMSR/WRMSR through the MSR permission map with its three ranges); exception intercepts by vector in `after_step` (info1 = error code, info2 = CR2 for #PF; `int3` counts as #BP, `int n` does not); physical interrupts (INTR intercept) and virtual interrupts (V_IRQ with priority/TPR, VINTR intercept) in `before_step`; triple fault with the shutdown intercept. Intercepts leave RIP on the intercepted instruction and report the following address in nRIP. The TSC offset applies to every guest TSC read. `vmexit` and `vmrun` flush the decode cache (`flush_decode`), which must not drop the JIT's code-page flags (stale blocks otherwise; see 18).

`exit_int_info`: a nested page fault while an event is being delivered (injected or taken by the guest) reports that event (valid bit, type, vector, error code) so the hypervisor can inject it again; no other exit has an event in flight, because intercepts happen at instruction boundaries.

Nested paging (`nested_translate`, used by `walk` for every guest page-table read, A/D update and the final address): a 4-level walk of `nCR3` (2 MiB and 1 GiB pages, NX when the host's EFER.NXE is set, the User bit required at every level), setting A/D bits; a failure is `VMEXIT_NPF` with EXITINFO1 = present/write/user/reserved/fetch plus bit 32 (final address) or 33 (guest page-table walk) and EXITINFO2 = the guest-physical address. The soft TLB is flushed at every entry and exit, so it never mixes guest and host translations.

**Limits, stated plainly**: a guest may be in any mode the CPU runs: real mode (the architectural reset state a hypervisor starts a vCPU in), virtual-8086, 16/32-bit protected, 32-bit and PAE paging (the PDPTEs are latched at `vmrun`, through nested paging when it is on; an invalid one is `VMEXIT_INVALID`; the host's own PDPTEs come back at #VMEXIT), compatibility and 64-bit mode (see 15). EFER.LMA is derived as LME and PG, and the long-mode consistency checks (PE, PAE, not both CS.L and CS.D) apply only when long-mode paging is on. Not implemented: a guest that itself runs `vmrun` (nested virtualization; the VMRUN intercept is mandatory), AVIC, LBR virtualization, decode assists, the PAUSE filter, V_INTR_MASKING's use of the host's IF, V_GIF, SKINIT (#UD), SMM/INIT/NMI intercepts, task-switch intercepts, and IRET/POPF interrupt-inhibit nuances. **Verification**: 43 unit tests drive a hand-built VMCB and a guest snippet through the real run-loop pieces (`before_step`/`step`/`after_step`), with 12 of the scenarios repeated on the JIT; Linux 6.18 sees `svm npt nrip_save vmcb_clean flushbyasid`. It has been run against a real nested hypervisor: `hack/kvm/run.sh` boots Alpine's 64-bit kernel, loads `kvm.ko`/`kvm-amd.ko` (6.18; "Nested Paging enabled"), and a static `/kvmtest` creates KVM vCPUs that run in real mode, 32-bit protected mode, long mode, PAE paging and 32-bit paging, printing through port 0x3f8 (IOIO intercept) and halting (HLT intercept) under nested paging, with KVM resolving the nested page faults. All five pass. Xen 4.21 then ran as the L1 hypervisor with a PVH Linux dom0 and a PVH domU (see 18, step 6), which exercises what KVM does not: Xen leaves CR0/CR3 writes unintercepted under nested paging and learns about long mode from EFER.LMA in the VMCB, which #VMEXIT therefore saves (it used to be stripped), and its `vmcall`/`vmmcall` hypercalls, event channels, ASID changes and NPT with 2 MiB and 1 GiB pages all work. Not run: a Windows L2 and KVM's more exotic exits. Found by the JIT scenarios: the JIT inlined `f3 90` (pause) as a nop, so the PAUSE intercept never fired; it now goes through `exec`. Found by KVM: a guest with paging off skipped nested translation (its linear addresses are guest-physical), so a real-mode L2 ran whatever sat at the same host-physical address; fixed in `walk` and covered by `a_guest_without_paging_still_goes_through_the_nested_tables`. `uemulator advanced boot --debug` logs every `vmrun` and #VMEXIT (code, exit info, guest CS and RIP).

## Control-register rules outside long mode

`write_cr0`/`write_cr3`/CR4 writes/EFER follow SDM 2.5 and 9.8.5: CR3 is 32 bits wide unless EFER.LMA (bits 63:32 are #GP; 32-bit paging keeps bits 31:12 plus PWT/PCD, PAE keeps 31:5 plus PWT/PCD and latches the PDPTEs, #GP on a malformed present entry before CR3 changes); EFER.LME may only change while CR0.PG is clear; setting CR0.PG with LME needs CR4.PAE and a non-64-bit code segment (CS.L clear); CR4.PCIDE needs EFER.LMA and CR0.PG cannot be cleared while PCIDE is set. Any CR0/CR3/CR4 write flushes the soft TLB; a change of paging format also flushes the decode cache. The JIT is unaffected: it only runs 64-bit code and inlines TLB probes that are filled from `translate` in whatever format was active, so the TLB is always flushed on a format change.

## AVX-512

Files (all children of `sse`, because the FP half needs the soft-float engine): `evex.rs` (state accessors, the generic operand/mask machinery, and the lane-wise table), `avx512_data.rs` + `avx512_lanes.rs` (moves, broadcasts, inserts/extracts, element moves), `avx512_int.rs` + `avx512_perm.rs` + `avx512_misc.rs` (integer, permutes, narrowing/widening, compress/expand, VBMI/VBMI2/IFMA/VNNI/BITALG/GFNI), `avx512_fp.rs` + `avx512_convert.rs` (compares, FMA, estimates, getexp/getmant/scalef/fixupimm/rndscale/reduce/range/fpclass, every conversion), `avx512_gather.rs`, `avx512_mask.rs` (the VEX-encoded opmask instructions). Tests: `evex_tests.rs` and its children (`evex_int_tests.rs`, `evex_perm_tests.rs`, `evex_fp_tests.rs`, `evex_conv_tests.rs`, `evex_lane_tests.rs`); encodings are generated by `hack/gen_avx512.py` from the instruction list in `hack/avx512_forms.py` (each form assembled with clang in xmm/ymm/zmm, plain/merge/zero-masked/memory/broadcast shapes, and with registers above 15), written to `avx512_encodings.rs` (`{evex}` forces the EVEX encoding where clang would pick VEX).

State: `Cpu::zmm_hi` (bits 511:256 of ZMM0-15), `zmm_extra` (ZMM16-31 whole), `opmask` (k0-k7); `xmm`/`ymm_hi` are unchanged so the JIT and every VEX path keep working. `Cpu::zmm(n)`/`set_zmm(n, v)` view a register as four 128-bit lanes (a `Vector`). Every VEX write now also zeroes bits 511:256 (`clear_zmm_upper`); vzeroupper/vzeroall clear ZMM0-15 only. XCR0 bits 5-7 (opmask, ZMM_Hi256, Hi16_ZMM) must be set together and need AVX; XSAVE components 5, 6, 7 sit at 1088 (64 B), 1152 (512 B) and 1664 (1024 B), the area is 2688 bytes, and CPUID.0xD reports all of it; `xrstor` reads every component before committing any. `Cpu::diff` and the test `Snapshot` compare the new state.

Decoding: `62` is EVEX in 64-bit mode (`Insn::evex`, `evex_mask`, `evex_zeroing`, `evex_b`, `evex_ll`). R', X (on a register operand) and V' extend `reg`, `rm` and `vex_v` to 5 bits; V' also extends a VSIB index. The P0/P1 reserved bits, a legacy/REX prefix before EVEX, and maps other than 1-3 are #UD (so AVX512-FP16, map 5/6, is #UD). The compressed disp8 is left raw (`evex_disp8`) and multiplied by the tuple size when the address is formed (`evex_address`: the vector length, the broadcast element, or the memory operand's own size), because only the instruction knows its tuple. `Insn::op` carries `EVEX_OP_FLAG`, so no VEX or legacy match can claim it; everything runs through `exec` (`exec_evex`), including in the JIT. Outside 64-bit mode `62` is `bound` (see 15).

Execution: `exec_vector_op` fetches vvvv and r/m (`fetch_rm`: register, memory with disp8 scale, or a broadcast element), runs the body and commits under the write mask (`commit_masked`: merge keeps the old element, EVEX.z zeroes it, everything above the vector length is zeroed). Most of the lane-wise instructions are the legacy SSE kernel on each 128-bit lane (`lane_spec`, through `run_legacy_registers`), which is also where all the packed/scalar FP arithmetic, shuffles and the byte/word integer set come from; lanes whose elements are all masked are skipped, so a masked-out element never raises a flag. The rest is native element code. Memory operands of masked instructions skip masked-out elements (fault suppression: a masked load or store crossing into an unmapped page does not fault unless a selected element is there); stores probe every page before writing. Embedded rounding and `{sae}` (`with_static_rounding`) run the body with MXCSR's rounding replaced and all exceptions masked, then restore MXCSR, so nothing is raised or recorded, as the SDM says. Gathers and scatters clear mask bits as elements complete and write partial state back before a fault, so they restart.

Implemented: AVX512F (all of it except the Xeon Phi-only ER/PF sets), VL, BW, DQ, CD, IFMA, VBMI, VBMI2, VNNI, BITALG, VPOPCNTDQ, GFNI, VAES, VPCLMULQDQ; the VEX-encoded opmask instructions (kmov in every width and form, kand/kandn/kor/kxnor/kxor/kadd/knot, kunpck, kshiftl/r, kortest, ktest). Floating-point notes: `vrcp14*`/`vrsqrt14*` return the correctly rounded result (hardware returns a ~14-bit estimate; the tests accept any result within 2^-14); `vgetmant` of an infinity returns 1.0 with the sign control applied, `vrange` resolves ties between equal magnitudes toward the first operand, and `vfixupimm` signals only the exceptions its immediate asks for. AVX512_BF16 (`avx512_bf16.rs`: `vcvtne2ps2bf16`, `vcvtneps2bf16`, `vdpbf16ps`; always round-to-nearest-even with DAZ/FTZ and no MXCSR flags, per the SDM; the odd bfloat16 pair is added before the even one, with a rounding in between, pinned by a test) and `vdbpsadbw` are implemented. Not implemented: AVX512_FP16, VP2INTERSECT, AVX512PF/ER (Xeon Phi).

Verification: ~200 unit tests (`cargo test -p uemulator evex`), each element-wise result against an independent loop or the host FPU (bit-exact for ordinary values; the specials against the SDM tables), every shape of every form, fault suppression/atomicity at an unmapped page, gather restart, XSAVE round trips, CPUID leaves, and a JIT-versus-interpreter case per family. Booting: Alpine reports `avx512f avx512dq avx512ifma avx512cd avx512bw avx512vl avx512vbmi avx512_vbmi2 gfni vaes vpclmulqdq avx512_vnni avx512_bitalg avx512_vpopcntdq` and reaches a shell; the Debian installer boots to its first dialog with glibc free to pick its EVEX string functions.

**Real-guest check (the "AVX is not working" report).** Unit tests only proved single instructions, so a guest was used: static x86-64 programs (`x86_64-linux-musl-gcc`) appended to the Alpine initramfs as a second cpio, run under `rdinit`. (1) A hash-per-operation program: every AVX/AVX2/FMA/F16C/SSE4/AES/CLMUL/SHA/BMI operation on special-value-heavy random data in all four MXCSR rounding modes plus DAZ/FTZ, ~530 results; run under `qemu-system-x86_64 -cpu max` (TCG has AVX2 but no AVX-512) every hash is identical to the emulator's, interpreter and JIT. (2) The same for AVX-512 can only be compared against the emulator itself, so (3) a program calling **one instance of every GCC AVX/AVX-512/BMI/AES/GFNI/VNNI/BF16 intrinsic with value operands (3,800 of them, generated from the compiler's headers)** under a SIGILL handler, to find instructions that are advertised but #UD: it found `vpsubsw` (EVEX.0F E9 missing from the lane table), `vdbpsadbw`, the SHA instructions and the BF16 set. All fixed; the JIT and the interpreter agree on every result. (4) XSAVE state under a 2 ms `setitimer` signal handler that clobbers zmm1/zmm17/k3, and four forked processes yielding with live zmm5/zmm20: no corruption. So the instruction semantics were right where they existed; what failed in real guests was the instructions that did not exist, and `clwb` executing as xsaveopt. `--verify` (lockstep JIT versus interpreter) on the arithmetic programs is below. The source of the programs is not in the repository (they are large generated files); the method is the whole recipe: one call per intrinsic in a `sigsetjmp` guard, FNV hash of every result vector. `--verify` on Alpine diverges at an interrupt entry (`0xffffffff810003c0`) with or without AVX-512 advertised, and the same on the checkout this branched from, so that is a pre-existing timing difference between the two device models and not an AVX-512 effect (not investigated further).
